*** Core Grammar Categories ***

Expressions 		-> calculations/conditions
Statements			-> executable actions
Control workflow	-> branching/loops
Data 				-> variables/payloads
Events				-> triggers
Pipelines			-> sequencing
Components			-> reusable modules


*** High-Level DSL Grammar ***

-> Root Structure
<program> ::= <workflow>

-> Workflow
<workflow> ::= {
    "type": "workflow",
    "nodes": <node_list>
}


-> Node List
<node_list> ::= [ <node>* ]


-> Generic Node
<node> ::= <action_node>
         | <control_node>
         | <event_node>
         | <data_node>



-> Action Node
<action_node> ::= {
    "type": <action_type>,
    "inputs": <object>,
    "outputs": <object>?
}


-> Control Node
<control_node> ::= <if_node>
                 | <loop_node>
                 | <parallel_node>




-> If Node
<if_node> ::= {
    "type": "if",
    "condition": <expression>,
    "then": <node_list>,
    "else": <node_list>?
}


-> Loop Node
<loop_node> ::= {
    "type": "loop",
    "iterator": <identifier>,
    "collection": <expression>,
    "body": <node_list>
}



*** Expression Grammar ***

-> Expressions
<expression> ::= <literal>
               | <variable>
               | <binary_expression>
               | <function_call>


-> Binary Expression
<binary_expression> ::= {
    "left": <expression>,
    "operator": <operator>,
    "right": <expression>
}


-> Operators
<operator> ::= "=="
             | "!="
             | ">"
             | "<"
             | ">="
             | "<="
             | "+"
             | "-"
             | "*"
             | "/"
             | "AND"
             | "OR"


-> Event Nodes
<event_node> ::= {
    "type": "event",
    "event": <identifier>,
    "handler": <node_list>
}


-> Function Calls
<function_call> ::= {
    "type": "call",
    "function": <identifier>,
    "args": [ <expression>* ]
}



-> Types
<type> ::= string
         | number
         | boolean
         | object
         | array
         | null



**** Task Type *****

action 		-> Performs a single operation. eg. send SMS, send email, charge payment, upload file, publish article

{
  "type": "action",
  "capability": "communication.email.send"
}

condition 	-> Branches execution.

{
  "type": "condition",
  "expression": "$user.isSubscribed == true",

  "onTrue": "send_email",
  "onFalse": "exit"
}

choice		-> Multi-path branching.

{
  "type": "choice",

  "expression": "$paymentMethod",

  "cases": {
    "momo": "hubtel_payment",
    "card": "paystack_payment"
  },

  "default": "unsupported"
}

loop 		-> Iterates over a collection.

{
  "type": "loop",

  "collection": "$subscribers",

  "body": "send_email",

  "next": "log_result"
}

parallel 	-> Runs multiple tasks concurrently.

{
  "type": "parallel",

  "tasks": [
    "send_sms",
    "send_email",
    "send_push"
  ],

  "next": "audit_log"
}

transform	-> Transforms data.

{
  "type": "transform",

  "operation": "filter",

  "input": "$users",

  "output": "activeUsers"
}

query		-> Reads data. eg. database query, API query, cache lookup

{
  "type": "query",

  "source": "users",

  "filter": {
    "active": true
  },

  "output": "users"
}

command		-> Changes state. eg. CRUD

{
  "type": "command",

  "command": "user.create"
}

Events	-> Publishes an event.

{
  "type": "event",

  "name": "article.published"
}


wait		-> Pauses execution.

{
  "type": "wait",

  "duration": "10m"
}

schedule	-> Schedules future execution.

{
  "type": "schedule",

  "cron": "0 8 * * *"
}

subflow	 	-> Executes another workflow.

{
  "type": "subflow",

  "workflow": "send_notifications"
}


script 	   -> Executes custom expressions.

{
  "type": "script",

  "language": "expr",

  "code": "price * quantity"
}

terminate  	-> Stops execution.

{
  "type": "terminate"
}

noop	   -> Does nothing. Useful during visual editing.

{
  "type": "noop"
}



**** Action Task Type *****

-> an action task type will depend on a system event 
-> define data sources (either internal to the system core or external)
-> define other inputs
-> define outputs
-> can also define other task types 

-> Action Task Node
<action_node> ::= {
    "type": "action",
    "capability": <string>,
    "on_event": <system_event>?,
    "data_sources": [ <data_source>* ]?,
    "prompt_config": <prompt_config>?,
    "inputs": <object>,
    "outputs": <object>?,
    "next_tasks": [ <task_reference>* ]?
}

-> Prompt Configuration (Handles display and user interaction)
<prompt_config> ::= {
    "message": <string> | <expression>,
    "interaction_type": "display" | "input" | "menu",
    "input_validation": <expression>?,
    "timeout_ms": <number>?
}

-> System Event Hook
<system_event> ::= {
    "event_name": <string>,
    "trigger_condition": <expression>?
}

-> Data Source Definition
<data_source> ::= {
    "name": <string>,
    "scope": "internal" | "external",
    "provider": <string>,
    "config": <object>?
}

-> Task Reference (For defining or linking other task types)
<task_reference> ::= {
    "task_id": <string>,
    "execute_condition": <expression>?
}


** Example **

{
  "type": "action",
  "capability": "finance.payment.process",
  
  "on_event": {
    "event_name": "checkout.completed",
    "trigger_condition": {
      "left": "$order.total",
      "operator": ">",
      "right": 0
    }
  },
  
  "data_sources": [
    {
      "name": "crm_db",
      "scope": "external",
      "provider": "postgresql",
      "config": {
        "connection_string": "env.CRM_DB_URL"
      }
    },
    {
      "name": "system_cache",
      "scope": "internal",
      "provider": "redis"
    }
  ],
  
  "inputs": {
    "amount": "$order.total",
    "currency": "$order.currency",
    "customer_id": "$user.id"
  },
  
  "outputs": {
    "transaction_id": "$response.tx_id",
    "status": "$response.status"
  },
  
  "next_tasks": [
    {
      "task_id": "send_receipt_email",
      "execute_condition": {
        "left": "$response.status",
        "operator": "==",
        "right": "success"
      }
    }
  ]
}

***** Transform Task Type *****

-> Transform Node
<transform_node> ::= {
    "type": "transform",
    "operation": "filter" | "map" | "project" | "merge",
    "input": <expression>,
    "mapping": <object> | <string>?,
    "output": <string>
}


** Example **

1. Example A: Functional Transformation (e.g., Filtering an Array)
This matches your exact source format, where a built-in operation filters a collection based on a condition.

{
  "type": "transform",
  "operation": "filter",
  "input": "$users",
  "mapping": "$item.active == true",
  "output": "activeUsers"
}


2. Example B: Structural Projection (Schema Mapping)
If you need to rewrite an API payload's keys to match a downstream system's expected schema, you can use a dictionary mapping:

{
  "type": "transform",
  "operation": "project",
  "input": "$api_response.data",
  "mapping": {
    "customer_id": "$input.id",
    "full_name": "$input.attributes.name",
    "contact_number": "$input.phone"
  },
  "output": "formattedCustomer"
}


***** Query Task Type *****

-> Query Node
<query_node> ::= {
    "type": "query",
    "source": <string>,
    "filter": <filter_expression>,
    "limit": <number>?,
    "output": <string>
}

-> Filter Expression
<filter_expression> ::= <object> | <expression>



** Example **

1. Example A: Database Lookups (Structured Filters)

{
  "type": "query",
  "source": "users",
  "filter": {
    "active": true,
    "country": "GH"
  },
  "limit": 50,
  "output": "activeUsers"
}


2. Example B: API-Driven Lookups (Dynamic Expressions)

{
  "type": "query",
  "source": "payment_gateway.transactions",
  "filter": {
    "left": "$transaction.status",
    "operator": "==",
    "right": "pending"
  },
  "output": "pendingPayments"
}


***** Command Task Type *****

-> Command Node
<command_node> ::= {
    "type": "command",
    "command": <string>,
    "http_request": <http_request_config>?,
    "output": <string>?
}

-> HTTP Request Config for http.* commands only
<http_request_config> ::= {
    "url": <expression>,
    "auth": <http_auth_config>?,
    "headers": <object>?,
    "query": <object>?,
    "body": <object> | <string>?,
    "timeout": <number>?
}

-> HTTP Auth Config
<http_auth_config> ::= {
    "type": "basic",
    "username": <expression>,
    "password": <expression>
}


** Example **

1. Example A: Explicit Domain Actions (Task/Action Oriented)

{
  "type": "command",
  "command": "user.create",
  "payload": {
    "username": "$new_user.username",
    "email": "$new_user.email",
    "role": "subscriber"
  },
  "output": "createdUser"
}


2. Example B: Standard CRUD State Manipulation


{
  "type": "command",
  "command": "database.update",
  "payload": {
    "target": "accounts",
    "where": { "id": "$account.id" },
    "set": { "status": "active" }
  }
}

-> PAYMENT PLUGIN TYPE I

Based on your BNF grammar and the provided task types, here is a complete, well-defined DSL plugin for a **Payment Orchestration Workflow**.

This workflow handles both **Hubtel** and **Paystack**. It validates the incoming request, dynamically routes to the selected payment provider, handles provider-specific logic (like Basic Auth for Hubtel and currency conversion for Paystack), standardizes the response to extract the `checkout_url`, and emits an event for the frontend.

### Payment Orchestration Plugin (JSON DSL)

```json
[
  {
    "type": "noop",
    "id": "payment_initiated",
    "meta": {
      "label": "Triggered when frontend requests a payment checkout"
    }
  },
  {
    "type": "condition",
    "id": "validate_payment_request",
    "expression": {
      "left": "$amount",
      "operator": ">",
      "right": 0
    },
    "onTrue": "route_payment_provider",
    "onFalse": "reject_invalid_amount"
  },
  {
    "type": "switch",
    "id": "route_payment_provider",
    "expression": "$payment_provider",
    "cases": {
      "hubtel": "initiate_hubtel_payment",
      "paystack": "calculate_paystack_amount"
    },
    "default": "reject_unsupported_provider"
  },

  {
    "type": "command",
    "id": "initiate_hubtel_payment",
    "command": "http.post",
    "http_request": {
      "url": "https://api.hubtel.com/v1/merchantaccount/merchants/$hubtel_merchant_id/receive/mobilemoney",
      "auth": {
        "type": "basic",
        "username": "$HUBTEL_CLIENT_ID",
        "password": "$HUBTEL_CLIENT_SECRET"
      },
      "headers": {
        "Content-Type": "application/json"
      },
      "body": {
        "CustomerName": "$customer_name",
        "CustomerMsisdn": "$customer_phone",
        "CustomerEmail": "$customer_email",
        "Channel": "mobile-money",
        "Amount": "$amount",
        "PrimaryCallbackUrl": "$webhook_url",
        "ClientReference": "$order_id",
        "Description": "Payment for Order"
      },
      "timeout": 30000
    },
    "output": "hubtel_raw_response"
  },
  {
    "type": "transform",
    "id": "format_hubtel_response",
    "operation": "project",
    "input": "$hubtel_raw_response",
    "mapping": {
      "checkout_url": "$input.Data.CheckoutUrl",
      "provider": "hubtel",
      "reference": "$order_id"
    },
    "output": "standardized_checkout_data"
  },

  {
    "type": "script",
    "id": "calculate_paystack_amount",
    "language": "expr",
    "code": "$amount * 100",
    "output": "paystack_kobo_amount"
  },
  {
    "type": "command",
    "id": "initiate_paystack_payment",
    "command": "http.post",
    "http_request": {
      "url": "https://api.paystack.co/transaction/initialize",
      "headers": {
        "Authorization": "Bearer $PAYSTACK_SECRET_KEY",
        "Content-Type": "application/json"
      },
      "body": {
        "email": "$customer_email",
        "amount": "$paystack_kobo_amount",
        "currency": "$currency",
        "reference": "$order_id",
        "callback_url": "$webhook_url"
      },
      "timeout": 30000
    },
    "output": "paystack_raw_response"
  },
  {
    "type": "transform",
    "id": "format_paystack_response",
    "operation": "project",
    "input": "$paystack_raw_response",
    "mapping": {
      "checkout_url": "$input.data.authorization_url",
      "provider": "paystack",
      "reference": "$input.data.reference"
    },
    "output": "standardized_checkout_data"
  },

  {
    "type": "event",
    "id": "emit_checkout_url",
    "name": "checkout.url.generated",
    "payload": {
      "url": "$standardized_checkout_data.checkout_url",
      "provider": "$standardized_checkout_data.provider",
      "order_id": "$standardized_checkout_data.reference"
    },
    "next": "terminate_success"
  },

  {
    "type": "terminate",
    "id": "terminate_success",
    "status": "success",
    "message": "Checkout URL generated successfully. Redirecting user."
  },
  {
    "type": "terminate",
    "id": "reject_invalid_amount",
    "status": "failed",
    "error_code": "INVALID_AMOUNT",
    "message": "Payment amount must be greater than zero."
  },
  {
    "type": "terminate",
    "id": "reject_unsupported_provider",
    "status": "failed",
    "error_code": "UNSUPPORTED_PROVIDER",
    "message": {
      "left": "The payment provider '",
      "operator": "+",
      "right": "$payment_provider + ' is not supported.'"
    }
  }
]
```

### Key Grammar Implementations Used:

1. **`condition` Node**: Validates that the `$amount` variable is strictly greater than `0` using the `<binary_expression>` object format before proceeding.
2. **`switch` Node**: Acts as a multi-path router. It evaluates the `$payment_provider` string and routes to the correct provider's initialization block.
3. **`command` Node (`http.post`)**:
   * **Hubtel**: Uses the `<http_auth_config>` block to pass Basic Authentication credentials securely via environment variables.
   * **Paystack**: Because Paystack uses Bearer tokens (and the BNF strictly defines `auth` as `basic`), the token is correctly injected into the `headers` object.
4. **`script` Node**: Paystack requires amounts in the lowest currency denomination (e.g., Kobo/Cents). A native `expr` script multiplies the base amount by 100 before the API call is made.
5. **`transform` Node (`project`)**: Both providers return differently structured JSON payloads. The `project` operation maps the provider-specific API responses into a unified `standardized_checkout_data` schema so the frontend always receives a consistent payload.
6. **`event` Node**: Publishes a `checkout.url.generated` event containing the unified payload, allowing frontend websockets or listeners to trigger the redirect.
7. **`terminate` Node**: Handles explicit failure states (like invalid amounts or unsupported providers) utilizing the `<binary_expression>` concatenation to build dynamic error messages.
